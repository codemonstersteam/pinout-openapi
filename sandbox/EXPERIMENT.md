# Эксперимент — проверка гипотез логическим выводом

Цель: убедиться, что **постановка задачи корректна** — т.е. алгоритм «восстановить кусок OpenAPI из стаба
потребителя и сверить со спекой поставщика» даёт правильный вердикт на всех значимых изменениях контракта.
Метод: для каждого сценария — гипотеза → вывод по правилам алгоритма → фактический прогон `check.mjs` →
сверка. Совпало на всех ⇒ постановка верна.

## Дано (общие посылки)

**Восстановленный из стаба `consumed-contract`** (вывод `reconstruct`, см. прогон):

```
POST /transfers            шлёт  {from:string, to:string, amount:integer}   читает {transferId:string, status:string}
GET  /accounts/{id}/balance                                                 читает {balance:integer, currency:string}
```

**Правила сверки** (ядро `compareOp`):
- (R1) операция потребителя должна существовать у поставщика;
- (R2, контравариантно) `requires(provider) ⊆ sends(consumer)` — всё обязательное у поставщика потребитель шлёт;
- (R3, ковариантно) `reads(consumer) ⊆ provides(provider)` — всё, что потребитель читает, поставщик отдаёт;
- (R4) типы общих полей совпадают.

Нарушено хоть одно правило ⇒ **несовместимо**.

---

## Сценарий v1 — базовая (контроль)

**Гипотеза:** совместимо (стаб был сгенерён из этой же спеки).
**Вывод:**
- R1 ✓ обе операции есть.
- R2 ✓ поставщик требует `{from,to,amount}` ⊆ шлём `{from,to,amount}`.
- R3 ✓ читаем `{transferId,status}` ⊆ отдаёт `{transferId,status,fee}`; читаем `{balance,currency}` ⊆ отдаёт `{balance,currency}`.
  Заметь: `fee` поставщик отдаёт, но потребитель его **не читает** — лишнее у поставщика не мешает (ковариантность).
- R4 ✓ типы совпадают.
**Ожидаемо: ✅ совместимо. Факт: ✅. Сходится.**

## Сценарий v2a — добавили НЕобязательное поле в ответ (`promoCode`)

**Гипотеза:** совместимо — новое выходное поле потребитель не читает.
**Вывод:** меняется только `provides(/balance)` = `{balance,currency,promoCode}`. Проверяем R3:
`reads {balance,currency} ⊆ {balance,currency,promoCode}` ✓. Остальные правила не затронуты.
**Ожидаемо: ✅ совместимо. Факт: ✅. Сходится.**

> Вывод-следствие: расширение ответа поставщика **безопасно** для потребителя — алгоритм это подтверждает, а не
> ложно-тревожит. Это отличает `reads ⊆ provides` от наивного «сравнить два списка полей на равенство».

## Сценарий v2b — убрали поле из ответа (`currency`)  ← ключевой

**Гипотеза:** несовместимо — потребитель читает `currency`, поставщик его больше не отдаёт.
**Вывод:** `provides(/balance)` = `{balance}`. Проверяем R3: `reads {balance,currency} ⊆ {balance}`?
`currency ∉ {balance}` ⇒ **вложение нарушено** ⇒ ошибка `READS_FIELD_NOT_PROVIDED`.
**Ожидаемо: ❌ несовместимо. Факт: ❌ (`READS_FIELD_NOT_PROVIDED @ GET /balance: currency`). Сходится.**

> Это и есть та самая интуиция «поставщик убрал поле, а стаб его ждёт → ошибка». На открытой схеме наивная
> валидация примера пропустила бы это; проверка вложения `reads ⊆ provides` — ловит. Гипотеза, ради которой
> вся постановка, — подтверждена.

## Сценарий v2c — поставщик потребовал новое обязательное поле запроса (`idempotencyKey`)

**Гипотеза:** несовместимо — потребитель не шлёт обязательное поле.
**Вывод:** `requires(/transfers)` = `{from,to,amount,idempotencyKey}`. Проверяем R2:
`requires ⊆ sends {from,to,amount}`? `idempotencyKey ∉ sends` ⇒ нарушено ⇒ `MISSING_REQUIRED_REQUEST_FIELD`.
**Ожидаемо: ❌ несовместимо. Факт: ❌. Сходится.** (Контравариантность запроса — зеркало ковариантности ответа.)

## Сценарий v2d — сменили тип (`balance`: integer → string)

**Гипотеза:** несовместимо — потребитель читает `balance` как число.
**Вывод:** R3 по присутствию ✓ (`balance` есть), но R4: тип потребителя `integer` ≠ тип поставщика `string`
⇒ `TYPE_MISMATCH`.
**Ожидаемо: ❌ несовместимо. Факт: ❌. Сходится.**

## Итог логического вывода

| Сценарий | Изменение | Нарушенное правило | Ожидаемо | Факт |
|---|---|---|---|---|
| v1  | — | — | ✅ | ✅ |
| v2a | +необяз. поле ответа | нет | ✅ | ✅ |
| v2b | −поле ответа | R3 `reads ⊆ provides` | ❌ | ❌ |
| v2c | +обязат. поле запроса | R2 `requires ⊆ sends` | ❌ | ❌ |
| v2d | смена типа | R4 типы | ❌ | ❌ |

**5/5 совпадений гипотезы с фактом.** Вывод: постановка корректна —
1. ожидание потребителя действительно **восстановимо из стабов** его компонентных тестов (шаг `reconstruct` дал непротиворечивый `consumed-contract`);
2. сверка «восстановленный кусок ↳ спека поставщика» **ловит все три класса ломающих изменений** (удаление читаемого поля, новое обязательное поле запроса, смена типа) и **не ложно-тревожит** на безопасном расширении ответа;
3. асимметрия направлений (`reads ⊆ provides` для ответа, `requires ⊆ sends` для запроса) — необходима: обе стороны проверены отдельными сценариями (v2b vs v2c), убрать любую = пропустить класс ошибок.

Значит модель BR (`../TASK.md`, §«Как работает проверка») подтверждена экспериментально на sync-протоколе;
async-зеркало (`send`/`receive` payload) следует той же алгебре вложений.

## Как воспроизвести

```
cd sandbox && npm install && node check.mjs
```

Единственная зависимость — `js-yaml` (спеки в YAML, как в проде). Правится сценарий в `scenarios/*.yaml`
или стаб в `consumer/component-tests/provider-stub.yaml` — прогон покажет новый вердикт.
