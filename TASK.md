# pinout-openapi — валидатор синхронных контрактов (Go CLI)

> Часть экосистемы [pinout](../pinout/README.md) (эпик E1). Симметричен `pinout-asyncapi` по конфигу и
> формату отчёта. Проверка совместимости пары **потребитель↔поставщик** по OpenAPI, на pre-merge стадии в CI.

## Статус задачи

**Бизнес-требование зафиксировано, модель ИСПРАВЛЕНА (пока направление — доработаем позже).**
Предыдущая реализация построена на **неверной модели** (сравнение двух ПОЛНЫХ OpenAPI-спек + плоская
сверка имён полей). Ниже — правильная модель, к которой приводим инструмент.

## Проблема

В CI, до мержа, детерминированно ответить: **совместим ли потребитель REST-API с master-спекой
поставщика** — до рантайма и без публикации клиентских библиотек. Несущий инвариант экосистемы: каждый
сервис конформен своей спеке (доказано его компонентными тестами), поэтому структурная совместимость
спек-пары ⇒ реальная совместимость сервисов.

## Правильная модель (несущие бизнес-требования)

1. **Источник истины — спека ПОСТАВЩИКА.** Инструмент грузит master-OpenAPI поставщика в структуру
   (`kin-openapi`: parse + резолв `$ref` + валидация → `openapi3.T`).
2. **Что зовём — из конфига потребителя.** `contract-tests.yaml` перечисляет операции (path+method),
   которые потребитель реально вызывает у поставщика. Сверяем ТОЛЬКО их.
3. **Ожидание потребителя — из его КОМПОНЕНТНЫХ ТЕСТОВ (заглушек), не из отдельной спеки.** Реальный
   потребитель (напр. брокер-интеграция, дёргающая REST под капотом) не ведёт отдельный «ожидаемый
   OpenAPI поставщика». Его ожидание живёт в **contract-true заглушках** его компонентных тестов: какой
   **request** он шлёт и какой **response** он ждёт (инстансы, а не схема).
4. **Механизм — валидация ИНСТАНСОВ заглушек против СХЕМЫ поставщика** (`openapi3filter`), а не диф двух
   спек и не плоская сверка имён:
   - request потребителя (из заглушки) — **принимается** схемой запроса поставщика для этой операции?
   - response, на который расчитывает потребитель (из заглушки) — **валиден** по схеме ответа поставщика?
   - **Глубина сравнения приходит даром:** валидатор схемы `kin-openapi` рекурсивен и знает JSON Schema
     (вложенность, типы, `enum`, `format`, `nullable`) — отдельной «v2-эпопеи глубокого сравнения» не нужно.
   → вердикт `совместимо | несовместимо` + структурированный отчёт (`error.code`, location) симметрично
   `pinout-asyncapi`.

## Что инструмент НЕ делает (границы)

- **Не сравнивает две полные OpenAPI-спеки** и не сверяет плоские имена полей (это была неверная модель).
- **Не поднимает стабы и не гоняет тесты** — чистая функция валидации в CI.
- **Не детектит breaking-change во времени** (провайдер v1→v2) — это `pinout-netlist` (эпик E2), и именно
  там уместен `oasdiff` (диф двух версий одной спеки). Для пары consumer↔provider `oasdiff` — не тот инструмент.
- Не проверяет, что сервис конформен своей спеке — это компонентные тесты самого сервиса (несущий инвариант).

## Открытые вопросы — НУЖНО ПРОРАБОТАТЬ (не решено, не выдумывать)

1. **Формат/расположение заглушек потребителя.** Откуда именно инструмент читает ожидание — WireMock-стабы,
   `.feature`-фикстуры, отдельный каталог? Как из инстанса заглушки извлечь request+response для операции?
2. **request-инстанс vs схема.** Что именно валидировать в запросе (path/query/headers/body) и как маппить
   заглушку на операцию поставщика (path+method)?
3. **Режимы отказа → exit-коды + `error.code`** (совместимо / несовместимо / операция не найдена у поставщика /
   спека недоступна / заглушка не парсится / …) — таксономия и мап в exit-коды.
4. **Поставщик** — спека по `spec_url` / `spec_path` / оба? Auth к приватному git? Таймаут-поведение?
5. **Формат отчёта** — согласование с `pinout-asyncapi` (общий канон, `schema_version` для netlist).
6. **Границы MVP** — что точно входит в первую версию, что отложено.
